# 前端对接说明 × 算法与整体规划

> 版本定位：**V0.3 本地联调版**（2026-09-19）｜ 前端：智能排产助手前端（本地托管页面，`apps/web/static/`）
> 后端：智能排产助手-v1 排产引擎（批次化多目标启发式）+ FastAPI 交互层
> ⚠️ 本方案定位为**本地联调与路演演示**，不是真实生产环境的正式对接方案。完成《前端对接方案问题汇总》P0、P1 问题并按第八章验收标准通过后，才能进入正式前后端联调与生产验收。
> 本文目的：前端同学照第三章的字段对照表完成对接；算法与规划口径看第五章；部署/安全/版本约束看第一、六、七章。

## 一、部署与接入方式（P0-01 / P0-02 修订，先读这个）

### 1.1 唯一正式接入方式：同源 API 自动加载

前端页面由 **FastAPI 托管**（`apps/web/static/`），前端启动时以**同源相对地址**拉取数据，禁止跨机混合内容访问：

```js
// apps/web/static/app.js 的 bootstrap() —— 主页面加载即调用
fetch('/api/dashboard').then(r => r.json()).then(d => { /* 更新页面变量并重渲染 */ });

// 数据分析页加载时调用
fetch('/api/analysis').then(r => r.json()).then(d => { /* 渲染分析页 */ });
```

- 主页面加载 → `GET /api/dashboard`；
- 数据分析页加载 → `GET /api/analysis`；
- 调单/重排成功后由前端重新 fetch 并重渲染刷新页面；
- **不存在也不使用 `window.applyBackendData` / `window.applyAnalysisData` 全局注入函数**——此前文档描述的注入契约为 GitHub Pages 演示版专用且未纳入本项目仓库，为避免两套互不兼容的契约，**统一按本节同源 API 方案对接**。若线上 Pages 版确需这两个函数，必须把该前端版本源码纳入同一仓库和版本管理后另行约定。

### 1.2 已废弃的桥接方式（勿再使用）

❌ 公网 HTTPS 页面（GitHub Pages）直接 fetch `http://127.0.0.1:8765`：HTTPS→HTTP 混合内容拦截、私网访问限制、`127.0.0.1` 语义指向访问者本机而非统一后端，CORS 中间件解决不了这些问题。本文原第一章的桥接脚本**作废**。

### 1.3 备选部署路线（正式环境任选其一）

1. 路演电脑直接访问 FastAPI 托管页面 `http://127.0.0.1:8765`（当前默认，1.1 即此方式）；
2. 前后端部署到同一 HTTPS 域名；
3. 后端使用 HTTPS 公网服务；
4. 受控 HTTPS 反向代理 / 临时隧道；
5. 打包桌面应用，由本地应用访问本机后端。

## 二、后端 API 总表

### 2.1 现有接口（V0.3 已实现）

| 接口 | 方法 | 用途 | 对应前端板块 |
|---|---|---|---|
| `/api/dashboard` | GET | 指挥总览全部数据（KPI/机台/甘特/风险/订单/问题单） | 总览页 bootstrap() |
| `/api/schedule/history?month=YYYY-MM` | GET | 正式排程历史版本摘要（可按计划月加载，最近 100 版） | 月份→周计划→周内版本选择器 |
| `/api/schedule/history/{schedule_version}` | GET | 指定历史版本的只读完整 dashboard 快照 | 历史甘特图回看 |
| `/api/analysis` | GET | 数据分析页数据 | 分析页 bootstrap() |
| `/api/problems` | GET | 问题单队列（原因 + 延期原因，逐单） | 风险预警 / 需人工确认 |
| `/api/priority` | POST | 人工调优先级（紧急/超时/普通），重排并返回前后 KPI | AI 排产顾问·人工调序（现状局限见 3.6） |
| `/api/data-summary` | GET | 数据底座体检（订单量/匹配率/设备台账） | 数据管理 |
| `/api/health` | GET | 存活探针 | — |

启动：`python -m uvicorn apps.web.main:app --port 8765` → http://127.0.0.1:8765

### 2.2 规划接口（正式版契约，对应问题汇总 P0-05/P0-06/P1-04/P1-05/P2-02）

```text
前端
  ├─ GET  /api/schedules/current/dashboard          （= 现 dashboard 的版本化形态）
  ├─ GET  /api/schedules/current/analysis
  ├─ GET  /api/schedules/current/problems
  ├─ GET  /api/orders?page=1&page_size=50&status=exception&keyword=...
  ├─ GET  /api/orders/{order_id}                     （订单详情：原始字段/延期容忍/违约金/违约金排序/清洗状态/排程状态/三工序时间/批次/设备/风险/约束解释/人工操作记录）
  ├─ PATCH /api/orders/{order_id}/delivery-policy    （企业人工维护延期容忍度与违约罚款信息）
  ├─ POST /api/orders/{order_id}/priority            （= 现 /api/priority 的 RESTful 形态）
  ├─ POST /api/tasks/{batch_id}/lock                 （任务锁定，持久化 + 审计）
  ├─ POST /api/tasks/{batch_id}/unlock
  ├─ POST /api/replan                                （插单/故障/缺料/恢复/锁定，方案A最少扰动 vs B最少延期）
  ├─ POST /api/schedules/rebuild                     （后台任务：返回 job_id，避免同步长请求）
  └─ GET  /api/jobs/{job_id}                         （进度/结果/失败原因）
```

**统一响应结构（所有接口，P2-01）**：

```json
{
  "ok": true,
  "request_id": "...",
  "schedule_version": 12,
  "data": {},
  "warnings": [],
  "error": null
}
```

错误响应必须含：错误代码、人类可读说明、是否可重试、相关订单/批次、当前排程版本。

**版本与并发（P1-04）**：每次排程生成 `schedule_version / created_at / created_by / parent_version / input_data_version / status`；所有写请求携带 `expected_schedule_version`，不一致返回 `409 Conflict` 要求刷新重试。服务重启后人工覆盖不得静默丢失（需持久化）。

**长任务异步化（P1-05）**：全量排程改走 `POST /api/schedules/rebuild → job_id → GET /api/jobs/{job_id}`，配合单实例排程锁、结果缓存、进度状态、超时与去重。当前 V0.3 的 dashboard/analysis/priority 仍是同步触发排程，首次加载可能明显超过十几秒，前端必须给加载态。

**订单延期政策正式契约（规划，V0.3 尚未实现）**：`dashboard / orders / problems / priority / replan` 的订单对象必须统一返回：

```json
{
  "delay_tolerance_days": 3,
  "delay_tolerance_source": "manual_import",
  "delay_tolerance_updated_by": "planner_01",
  "delay_tolerance_updated_at": "2026-09-19T10:00:00+08:00",
  "delay_tolerance_note": "客户书面确认可延期三天",
  "penalty_amount": 15000.00,
  "penalty_currency": "CNY",
  "penalty_rule": "fixed",
  "penalty_amount_source": "manual_import",
  "penalty_updated_by": "planner_01",
  "penalty_updated_at": "2026-09-19T10:00:00+08:00"
}
```

字段校验规则：`delay_tolerance_days` 只允许 `0 / 3 / null`；**每张参与排程的订单都必须由企业人工导入大于0的 `penalty_amount`**，并明确币种和计算规则；缺少违约金的订单不得进入自动排程，应进入人工确认队列。算法按同一比较口径计算订单违约成本并从高到低确定保护顺序，不再使用高/中/低等级代替真实金额。任何修改必须记录修改前后值、维护人、时间、依据和排程版本。V0.3 当前未真实返回这些字段，前端不得伪造。

## 三、板块 ↔ 字段对照（前端照此取数）

### 3.1 生产指挥总览 KPI 卡（`d.kpi`）

⚠️ **口径修订（P1-01）**：旧文档同时列 `on_time_rate` 与 `on_time_rate_fresh` 两个"不同口径"，但引擎 `result.on_time_rate` 本就以非积压单为分母、`fresh_on_time_rate` 又引用同一结果，**两字段当前值可能完全相同**。正式契约改为以下四字段，并同时返回**分子/分母**（前端不得只拿百分比展示）：

| 字段（目标契约） | 口径 | 分子/分母示例 |
|---|---|---|
| `on_time_rate_all` | 全部有效订单口径的准时率 | `{on_time, eligible, rate}` 如 `{73, 92, 0.7935}` |
| `on_time_rate_fresh` | 排除基准日前积压单后的准时率 | 同上结构 |
| `within_tolerance_rate` | 企业人工标记“可延期3天”的有效订单中，在原交期后72小时内完成的订单占比；分母包含准时完成和容忍窗内完成的可延期订单 | `{within_tolerance, eligible_tolerant, rate}` |
| `scheduled_rate` | 成功进入有效计划的订单占比（分母含被门禁/落位失败剔除的单） | 同上结构 |

**过渡说明（V0.3 现状）**：现有接口仍返回 `on_time_rate` 与 `on_time_rate_fresh`（值相同），前端可先按"准时率"单一语义消费，待 2.2 版本化接口落地后切换四字段。严格口径定义见 5.6。

其余 KPI 字段不变：

| 前端显示 | 字段 | 口径 |
|---|---|---|
| 产能利用率 | `kpi.utilization` | 三工段平均利用率；分子 = 加工+换型占用，分母 = 统一计划周期 |
| 设备数 | `kpi.device_total` | 从设备台账表头实取，非写死 |
| 拥堵设备 | `kpi.congested` | 利用率 >95% 的机台数 |
| 风险订单 | `kpi.risk_orders` | 超期单（容忍内 + 严格超期）合计 |

### 3.2 工段设备态势 / 数字孪生（`d.machines[]`，每台设备一条）

⚠️ **状态口径修订（P1-02）**：当前后端 `status` 只有 4 个值，且"未来 14 天窗口内有任务"就可能标 `normal`，**不代表设备此刻真实状态**。正式契约按"仿真时刻"拆分为 7 态：

| 状态 | 含义 |
|---|---|
| `running` | 当前时刻位于加工任务区间内 |
| `changeover` | 当前时刻位于换型块内 |
| `queued` | 当前空闲，但未来已有已排任务 |
| `idle` | 当前及近期均无任务 |
| `down` | 故障或检修（需接实时设备状态源） |
| `material_hold` | 缺料暂停（需接缺料事件） |
| `locked` | 当前任务已人工锁定 |

**过渡说明（V0.3 现状）**：接口现返回 `normal`（在制推断）/`idle` 待排/`change` 换型推断/`risk` 高负荷，前端展示时**不得**将 `normal` 直接解释为"生产中"，应表述为"计划内在制"。

其余字段不变：

| 字段 | 含义 |
|---|---|
| `id` / `zone` | 设备编号 / 工段（拉丝·捻股·合绳） |
| `order` / `product` / `material` | 在制订单、产品规格、材料 |
| `capacity` | 利用率字符串（如 "45%"） |
| `queue` | 甘特窗口内任务数（等待队列） |
| `change` | 下一次换型时间 |
| `risk` | 风险描述（如「高负荷 >95%」） |
| `trace[]` | **约束依据**：`{rule, text, impact}`，指回 R1–R10 规则编号（AI 助手展示用） |

### 3.3 设备甘特图（`d.tasks[]` 行 + `d.gantt.labels` 时间轴）

| 字段 | 含义 |
|---|---|
| `tasks[].machine` | 行名（如 `8107 拉丝`） |
| `tasks[].bars[]` | 任务条：`label` 订单短号、`left`/`width` 百分比位置、`status`（normal/risk/change）、`title` 悬浮详情（含起止/工时/换型）、`order` 订单号、`machine` 设备号 |
| `gantt.labels` | 时间轴标签（每 2 天一个） |
| `engines` | `{scheduler, tasks, changeovers}` 引擎版本与任务/换型计数 |

窗口 = 排产基准日起 14 天，按负荷取最忙 36 台。

### 3.4 风险预警（`d.risks[]`：`level/title/text/time/machine`）

规则驱动、全部可解释：引擎超期统计（R8）、R6 间隔违反、人工确认队列汇总、已逾期/临期订单统计、台账数据缺口。

### 3.5 订单池 / 订单中心（`d.orders` 二维数组）

**正式版目标表头**：`[订单号, 产品规格, 数量, 交期, 状态, 延期容忍标签, 违约金, 违约金顺位]`。状态在后端判定：已逾期 / 临期 / 正常 / 无交期 / 已完成（口径见 5.6）。V0.3 当前 `d.orders` 仍是旧五列结构，新增三列必须在后端真实返回相应字段后才能启用，前端不得用演示常量补齐。

**延期容忍标签（新增业务要求）**：由企业在订单导入或人工维护时明确填写，表示客户是否接受最多 3 天延期。该字段不是算法推断值，也不得根据“普通订单”身份自动赋值。

| 字段 | 允许值 | 前端标签 | 业务解释 |
|---|---|---|---|
| `delay_tolerance_days` | `0` | `不可延期`（红色） | 客户不接受延期；按原交期作为硬约束处理 |
| `delay_tolerance_days` | `3` | `可延期3天`（橙色） | 客户明确接受最多 72 小时延期；仅在无法全部准时交付时使用该容忍窗 |
| `delay_tolerance_days` | `null` / 未提供 | `容忍度待确认`（灰色） | 企业尚未确认客户政策；不得默认可延期，应进入人工确认或按不可延期保守处理 |

建议同时保留 `delay_tolerance_source`（如 `manual_import`）、`delay_tolerance_updated_by`、`delay_tolerance_updated_at` 与 `delay_tolerance_note`，用于说明标签来源、维护人、维护时间及客户约定。前端悬浮或详情说明统一显示：“该标签由企业人工导入，表示客户对交期后最多 3 天的容忍度，不代表系统承诺一定延期。”

**违约金标签（新增业务要求）**：所有订单都有违约金，具体金额与计算方式由企业人工导入。前端显示 `违约金 ¥金额` 和 `违约保护顺位 N`；悬浮解释统一为：“违约金由企业人工导入。排产无法保证所有订单准时时，系统优先保护预计违约损失更高的订单；该顺位只影响未开工任务，不自动移动已开工或已锁定任务。”违约金属于敏感数据时，列表可仅显示顺位，详情页按权限显示金额，但后端仍必须保存真实可计算数值。

导入时应包含：`order_id / delay_tolerance_days / delay_tolerance_note / penalty_amount / penalty_currency / penalty_rule / updated_by / updated_at`。任一订单缺少延期容忍度时按不可延期保守处理；缺少违约金时进入人工确认，禁止用订单重量、价格或客户名称自行估算。

⚠️ **重要边界（P2-02）**：dashboard 出于首页摘要考虑只返回**优先展示的 8 条**订单，**不能作为订单中心完整数据源**。完整订单查询/详情走 2.2 规划中的 `GET /api/orders` 与 `GET /api/orders/{order_id}`（支持分页、状态筛选、关键词搜索）。

### 3.6 问题单与人工调单

**问题单查询**：`GET /api/problems` →
- `manual[]`（人工确认队列：`order_id/spec_raw/stage/tier/reason`）
- `exceptions[]`（异常决策队列：另含 `late_days` 延期天数 / `delivery` 交期 / `close_end` 完工时间 / `delay_cause` 延期原因 / `tier`）

对应"允许出问题但必须说明为什么出问题、延期原因"的需求，逐单可追溯。

**人工调单**：`POST /api/priority` `{order_id, tier}` → 返回 `before/after` KPI、`sort_index` 排位、`note` 说明。

⚠️ **两项已知局限（P0-03 / P0-04，正式版必须修复后才可全量开放调单）**：

1. **异常决策订单当前可能查不到**：接口按正常排程索引（`ctx_by_order` + `unscheduled`）查单，被门禁拦截进入 `result.exceptions` 的订单**不在索引中，可能直接 404**——恰恰是最需要提级的延期单。正式版将建立完整订单索引（正常排程 + 异常决策 + 落位失败 + 主数据异常），除缺合法工艺路线/关键字段的订单外一律允许调序。
2. **可能"假成功"**：当前响应只回 `ok:true`，订单重排后若仍留在异常/人工队列，`sort_index` 可能为空但前端会误显示成功。正式契约增加明确结果：

```json
{
  "ok": true,
  "accepted": false,
  "schedule_status": "exception",
  "reason": "提升优先级后仍无法满足72小时交接约束",
  "before": {},
  "after": {}
}
```

状态枚举：`scheduled` 已进入有效排程 / `exception` 完成重排但仍超容忍 / `manual` 缺数据或工艺无法自动排程 / `rejected` 校验失败。
**前端规则：仅当 `schedule_status == "scheduled"` 才显示"调单成功"；`exception`/`manual` 必须展示 `reason` 引导人工处理。**

### 3.7 数据分析页（`GET /api/analysis`）

| 字段 | 含义 |
|---|---|
| `source` | `"engine-v2"`（前端据此显示「数据来自算法引擎」） |
| `totalDevices` | 设备总数 |
| `changeoverCount` / `changeoverHours` | 换型块数 / 总换型时长 |
| `idleCount` | 空闲机台数（计划周期内无任务） |
| `manualQueue` | 人工确认队列 |
| `utilByProcess[]` | `{process, rate}` 三工段利用率 |
| `distribution[]` | 订单结局分布 `{label, count}`：准时/可延期且容忍内超期/不可延期违约/超过容忍窗/历史积压/人工队列/异常队列；V0.3 未接延期标签前仍使用旧分类 |
| `topDevices[]` | 利用率 Top8 `{code, process, rate}` |
| `reasons[]` | 出问题原因聚合 `{title, evidence, suggest}` |
| `quality[]` | 质量侧观察 `{process, issue, batch, cause, fix}` |

### 3.8 其余板块的对接说明与状态边界

## 五、算法与整体规划介绍

### 5.1 总体框架

**批次化多目标启发式排产**（可解释分层贪心，刻意不用黑盒优化器——评审硬性项）：

```
订单拆批 → 优先级排序（紧急>超时>普通）→ 批次在 拉丝→捻股→合绳 三道工序
逐层落位（JIT/ASAP + 多机并行 + DBR 节拍 + 分级 relax）→ 门禁裁决（带原因）
→ 固定点重排收敛 → KPI + 全链路 constraint_trace 输出
```

企业目标采用**分层字典序**，发生冲突时严格按以下顺序裁决，而不是使用含义不清的单一“准时率优先”：

1. 最小化所有订单的总违约损失，并优先保护预计违约金从高到低的订单；
2. 最大化严格准时交付率；
3. 最大化带“可延期3天”标签订单的容忍窗内履约率；
4. 在不牺牲前三项目标的前提下，提高拉丝、捻股、合绳各工序利用率并降低工序间负荷失衡；
5. 减少换型时间、跨工序等待和动态重排扰动。

上述目标是**正式版目标口径**。V0.3 现有代码仍需通过实验和代码核验确认是否完整实现，文档不得把规划目标写成已验证结果。

### 5.2 数据层

规格自由文本解析（绳径/股数/结构/绳芯）→ 产能索引（规格→可用机台+工时）→ `bridge_map` 结构学规则兜底缺失的股型/股径，推断值必标黄。

### 5.3 订单建模：拆批 + 双层优先级

- 拆批：单批目标 **24h**、上限 **12 批/单**（当前 config 生效口径；历史材料中 12h/≤4 批为旧口径，以代码 `config.py` 与本节为准），数量严格守恒；
- 客户延期容忍度：`delay_tolerance_days` 由企业人工导入，只允许 `0 / 3 / null`；`null` 不得自动视为可延期，默认按不可延期保守处理并提示人工确认；
- 约束口径分层 L1–L5：硬交期（不可延期/容忍度未知/企业明确指定硬约束的重点或插单）→ 可准时 → **仅带“可延期3天”标签订单**使用3天容忍窗 → 无望 → 历史积压；所有订单都有违约金，但“有违约金”本身不等于硬交期，违约金用于确定保护顺序和经济损失；
- 调单口径：**紧急(0) > 超时(1) > 普通(2)**，人工可通过调单接口覆盖档位（写「人工调单」trace，可审计）；`config.PRIORITY_ORDER_RULE` 一行可切回「分层>EDD」。

当受产能限制无法保证全部订单准时交付时，算法先按企业导入的违约金计算预计违约损失，按损失从高到低保护订单；可延期3天的标签只决定该订单是否允许使用72小时容忍窗，不会覆盖违约金排序。违约金相同时，依次按不可延期优先、紧急/重点优先、交期更早优先、换型与扰动更小优先确定先后顺序。所有订单的违约金和计算规则均由企业人工导入，算法不得臆测。

### 5.4 落位算法

1. **交期倒排**：算每道工序最早/最晚开工窗；捻股/合绳 JIT 锚定交期，拉丝 ASAP 滚动；
2. **单机 JIT**：链尾贴交期逆序排，减少在制品；
3. **多机并行**：有交期风险时逐级加并行（≤12 台），失败整段回滚；
4. **DBR 节拍控制**：拉丝完工不得跑赢捻股消化能力，否则 R6 交接冲突全剪空；
5. **分级 relax（口径修正）**：非硬交期单全失败时，先放开交期上限转 ASAP；若仍失败，**R6 交接超 72h 的任务不作为正常可执行计划输出**（R6 为硬约束，不得"软化"后伪装成正常计划），而是转逐批偏好提示并进异常/人工队列，逐单带原因——不丢单、也不伪装。

### 5.5 换型与选机

- 换型严格串行（开工 ≥ 前块完工 + 换型时长），不抢占；
- 切换幅度 5 档 → 1–5 小时；**合绳上股准备 = 股数×10 分钟**（6 股 +1h、8 股 +1.33h）；6 股与 8 股互为不同结构必须换型；
- 选机评分**分层字典序**（不可加权求和）：可行 (0, 最小换型, 最小负荷偏差)；不可行 (1, 最小延期, 最小换型, 最小负荷偏差)。

### 5.6 KPI 口径（V0.3 基础口径已实现；延期标签细分口径为正式版目标）

```
准时交付率 = 准时单数 ÷ 非积压单总数（分子/分母随接口返回，见 3.1 四字段契约）
margin_h = 交期 − 合绳链尾完工
margin ≥ 0 → 准时（计入分子）；
订单带“可延期3天”标签且 −72h ≤ margin < 0 → 容忍内超期（不计入准时，但计入容忍窗履约）；
订单为“不可延期”或“容忍度待确认”且 margin < 0 → 违约风险，不得套用 3 天容忍窗；
可延期订单 margin < −72h → 严格超期；积压单（交期早于基准日）不计入分子分母，单独统计
```

订单状态判定：`delivery < 基准日` 已逾期；`≤ 基准日+3天` 临期；否则正常（完成状态以表内结案代码为准）。

> 算法版本标识（P1-06）：正式版接口将返回 `algorithm_version / config_version / input_data_version / schedule_version`，前端展示与导出须随行，保证任何 KPI 数字可回溯到确定的算法与数据版本。

### 5.7 门禁 + 固定点重排 + 动态异常

- 不可延期订单或容忍度未知订单一旦超期 → 人工确认队列；仅带“可延期3天”标签的订单可使用 72 小时容忍窗，超过 3 天 → 异常决策队列，逐单带 `late_days / delay_cause / reason / tier / delay_tolerance_days / penalty_amount / penalty_rank`；
- 产能不足必须发生延期时，优先将延期分配给“可延期3天”且违约罚款较低的订单；不可延期、高罚款、重点、插单订单优先保护，以尽可能降低总违约罚款，而不是只追求表面准时率；
- 被拦订单批次回滚释放机时，固定点迭代重排直到无新失败；
- 动态异常（插单/故障/缺料）：冻结已开工/锁定/临近 24h 批次，输出最少扰动 vs 最少延期双方案（接口化见 2.2 `POST /api/replan`）。

### 5.8 工程纪律（评审硬性项）

每条排程必带 `constraint_trace` 指回 R1–R10；台账从表头实取；推断值必标黄；人工干预闭环完整（锁定→调整→重算→确认→留痕，接口化见 2.2）；不做黑盒优化器。

### 5.10 建模假设与适用边界

以下是假设，不是已证实事实；接入真实车间数据后必须逐项复核：

1. 当前排程从基准日当天 `00:00` 开始，基准日前没有未录入的在制任务占用设备；
2. 未说明紧缺的人力、模具、吊装、能源和辅料暂按满足当前订单处理，但系统应保留资源不足事件入口；
3. 设备加工块不可抢占；换型、上股准备与加工严格串行占用对应设备；
4. 订单必须按拉丝→捻股→合绳顺序生产，相邻工序至少预留2小时交接，等待不得超过72小时；
5. 同一订单允许拆批和多机并行，但数量严格守恒，每单最多12批、最多12台并行设备；
6. 产能取“产品额定（平均值）”中的平均能力，未建模随机波动时不得把结果表述为确定承诺；
7. `bridge_map` 推断的工艺匹配必须标识来源，不能与人工确认的主数据等价；
8. 客户延期容忍度和违约罚款完全由企业人工导入，算法不得自行猜测；
9. 设备故障、缺料、插单等动态事件发生后，以事件时间为新基准冻结已开工、已锁定及临近24小时任务，再局部重排；
10. 若实际存在班次、停机日历、维护计划或原料库存，则在上线前必须转为硬约束，不能继续假设为充足。

### 5.11 数学目标与约束表达

正式版采用分层字典序目标向量：

```text
min Lexicographic(
  Z1 = Σ_i P_i(T_i),                                  总违约损失
  Z2 = Σ_i 1[A_i = 0 且 T_i > 0],                     不可延期订单违约数
  Z3 = Σ_i 1[A_i = 72 且 T_i > 72],                   超出客户容忍窗订单数
  Z4 = Σ_i 1[T_i > 0],                                严格超期订单数
  Z5 = 工序利用率差异 + 低利用率惩罚,                 负荷均衡
  Z6 = 总换型小时 + 总等待小时 + 动态重排扰动量       生产稳定性
)
```

每张订单必须有企业导入的 `penalty_amount=F_i>0`。进入自动排程前先把未知容忍度订单送入人工确认；为保守预估风险可以暂按 `A_i=0` 展示，但不得把临时值写回主数据。`penalty_rule=fixed` 时，订单一旦超出其允许容忍边界，`P_i(T_i)=F_i`；`penalty_rule=per_day` 时，`P_i(T_i)=F_i×ceil(E_i/24)`，其中 `E_i=max(0,T_i-A_i)`；若企业还有按比例或封顶规则，必须以可审计公式配置。算法首先比较 `P_i(T_i)`，预计损失更高者优先；预计损失相同，再依次比较 `A_i`（不可延期优先）、紧急/重点标识、交期、换型成本和扰动量。核心硬约束至少包括：工艺先后、设备唯一占用、不可抢占、换型串行、数量守恒、2小时最小交接、72小时最大等待、客户延期容忍上限、设备适配和已锁定任务不可移动。

### 5.12 模型选择、Baseline 与备选方案

| 方案 | 用途 | 优点 | 局限 | 当前状态 |
|---|---|---|---|---|
| Baseline：EDD + 单机最早可用贪心 | 作为最低比较基准 | 简单、可复现、运行快 | 不充分考虑换型、并行和跨工序等待 | 待建立并运行 |
| 当前方案：批次化多目标启发式 | 展示版主算法 | 可解释、能处理大规模订单和复杂业务规则 | 不保证全局最优，参数敏感 | 已有实现，需系统实验验证 |
| 备选：MILP/CP-SAT | 小规模最优值或下界对照 | 约束表达严格，可评价启发式质量 | 大规模求解时间可能过长 | 待小样本验证 |
| 备选：遗传算法/NSGA-II | 多目标搜索对照 | 能探索非凸解空间 | 稳定性、解释性和运行时间需额外控制 | 非首选，仅作对照 |

选择当前启发式算法的理由是：赛题强调可解释性、真实工程规则和有限时间内响应；但“可解释”不等于“效果已证明”，必须通过5.13的实验与Baseline比较后才能形成结论。

### 5.14 敏感性、压力与鲁棒性分析

正式评审前至少完成以下实验：

1. 拆批目标时长取12、18、24、36小时；
2. 最大批次数和最大并行设备数分别取4、8、12；
3. 允许延期订单比例从0%逐步增加，观察总违约损失与严格准时率变化；
4. 违约金金额分布变化，检查订单保护顺序是否严格按预计违约损失从高到低执行；
5. 拉丝、捻股、合绳任一工序产能下降10%、20%、30%的压力测试；
6. 随机设备故障、缺料、紧急插单和恢复事件的局部重排测试；
7. 交接缓冲与最大等待边界测试，尤其验证2小时下界和72小时上界；
8. 与EDD Baseline比较排入率、严格准时率、容忍窗履约率、总违约损失、利用率和运行时间；
9. 在可由精确模型求解的小样本上比较启发式最优差距；
10. 重复运行检查确定性；若引入随机算法，报告多次运行均值、标准差和随机种子。

- 原始数据只读保存，清洗数据另存并记录逐条原因；
- 每次实验绑定 `input_data_version / algorithm_version / config_version / schedule_version`；
- 保存完整配置、运行日志、错误日志、结果明细和汇总指标；
- 所有图表必须由结果文件生成，不得使用演示或手工数据替代；
- “降低违约罚款”“提高准时率”“提高利用率”等结论，只有在Baseline和敏感性实验支持后才能写入结论；
- V0.3 未接实时设备、库存、在制品和报工，因此只能称为“计划仿真/决策支持”，不能表述为已验证的实时数字孪生或生产执行系统。

### 5.16 增加或减少设备后的动态重排算法（正式版规划，V0.3 尚未实现）

设备增减统一作为资源变更事件进入 `POST /api/replan`，不得由前端直接修改甘特图。事件类型包括：`machine_add` 新增设备、`machine_down` 突发故障、`machine_maintenance` 计划停机、`machine_remove` 永久移除、`machine_restore` 修复恢复。前端提交的是事实和业务选择，后端负责验证设备能力、重算产能并生成新排程。

#### 5.16.1 设备变更请求字段

```json
{
  "event_type": "machine_add",
  "device_code": "HS-009",
  "process": "合绳",
  "effective_at": "2026-09-20T08:00:00+08:00",
  "available_until": null,
  "capacity_profile_id": "cap-hs-009-v1",
  "supported_specs": ["6股", "8股"],
  "initial_setup_state": "6股",
  "affected_task_policy": "freeze_started",
  "expected_schedule_version": 12,
  "reason": "新增设备投入生产"
}
```

| 字段 | 规则 |
|---|---|
| `event_type` | 必填，只允许上述5种设备事件 |
| `device_code` / `process` | 必填，设备编号唯一且工序不可为空 |
| `effective_at` | 事件实际生效时间，不得早于已经确认的报工时间 |
| `available_until` | 临时设备或计划停机时填写；永久有效可为空 |
| `capacity_profile_id` | 新增或恢复设备必须引用已确认的产能档案，禁止凭设备数量平均分摊产能 |
| `supported_specs` | 可加工规格白名单；未匹配规格不能分配到该设备 |
| `initial_setup_state` | 决定首个任务是否产生换型时间 |
| `affected_task_policy` | 默认冻结已开工、已完成、已锁定及临近24小时任务 |
| `expected_schedule_version` | 乐观锁；版本不一致返回409，禁止覆盖他人调整 |
| `reason` | 必填，进入审计日志和排程解释 |

#### 5.16.2 通用处理流程

```text
接收设备事件
→ 校验事件、设备台账、产能档案、规格能力、版本和生效时间
→ 复制当前排程形成候选版本，不直接覆盖已发布版本
→ 按事件时刻划分冻结任务与可移动任务
→ 更新设备可用日历和产能索引
→ 找出受影响订单及其上下游批次
→ 先修复硬约束可行性，再按字典序目标优化
→ 生成方案A“最少扰动”和方案B“最少违约损失”
→ 独立校验全部硬约束与KPI
→ 返回新旧差异，等待人工确认发布；失败则回滚
```

冻结集合包括：事件发生前已完成任务、已经开工且能够安全继续的任务、人工锁定任务，以及默认24小时冻结窗内任务。突发故障设备上正在加工的任务不能假设自动完成：必须由企业选择“报废重做、剩余量转机、原机修复后继续”之一，并录入已完成数量、剩余数量和质量状态。未收到选择前，该任务进入人工确认队列。

#### 5.16.3 增加设备算法

1. 校验新增设备属于拉丝、捻股或合绳中的哪一工序，并加载该设备真实产能、可加工规格、换型规则、启用时间和初始状态；
2. 在 `effective_at` 前不允许分配任务，若为临时设备则在 `available_until` 后禁止分配；
3. 保留冻结任务不动，把新增设备加入对应工序候选设备集；
4. 优先扫描当前异常队列、不可延期风险单、高罚款订单和超过瓶颈工序能力的批次；
5. 对可移动任务计算迁移收益：违约损失减少量、严格超期减少量、交接冲突减少量、负荷均衡改善量，减去新增换型、搬运、重检和扰动成本；
6. 只有收益为正且所有硬约束通过时才迁移；不能为了提高新增设备利用率而移动本来准时且稳定的任务；
7. 新增设备若位于非瓶颈工序，应受下游消化能力限制，避免上游过量提前生产导致等待超过72小时；
8. 输出新增设备实际承接任务、减少的违约风险、对其他设备释放的机时，以及仍无法解决的订单。

新增设备候选任务采用字典序评分：

```text
score_add(task, machine) = Lexicographic(
  hard_violation_count（必须为0，否则候选淘汰）,
  -预计减少的违约损失,
  -减少的严格超期小时,
  新增换型与搬运成本,
  对已发布任务的扰动数量,
  设备完工时间
)
```

#### 5.16.4 减少设备或设备故障算法

1. 将设备从 `effective_at` 起标记为不可用；计划停机可在停机窗口结束后恢复，永久移除则不再进入候选集；
2. 保留停机前已完成任务；对跨越停机时刻的在制任务按企业选择处理剩余数量，禁止重复计算已完成产量；
3. 撤销该设备生效时间后的未开工任务，并恢复这些任务对应的设备时间、数量和上下游依赖；
4. 按“不可延期/高罚款→重点/插单→临近交期→可延期低罚款”的顺序形成待迁移队列；
5. 先在同工序、同规格能力的设备中寻找可行空档，再尝试拆批和多机并行；每次试排失败必须完整回滚，不得残留试算任务；
6. 重排后重新检查拉丝→捻股→合绳顺序、2小时最小交接、72小时最大等待、换型串行、设备冲突、数量守恒和客户延期容忍；
7. 若全部任务无法排入，优先把延期分配给带“可延期3天”且违约成本较低的订单；不可延期或高罚款订单进入人工确认并给出缺口；
8. 输出受影响订单、迁移批次、预计延期、罚款变化、工序产能缺口和建议恢复时间，不得只返回“重排失败”。

减少设备时的候选落位评分：

```text
score_remove(task, machine, slot) = Lexicographic(
  hard_violation_count（必须为0，否则候选淘汰）,
  新增违约损失,
  严格超期小时,
  是否超过客户延期容忍,
  换型与搬运成本,
  被扰动的其他任务数,
  工序负荷偏差
)
```

#### 5.16.5 设备恢复算法

设备恢复不能简单等同于新增设备。后端应先确认维修验收时间、恢复后的产能档案、可加工规格和初始换型状态；原设备上的历史未完任务只有在质量与剩余量确认后才能继续。恢复后采用新增设备算法寻找改善机会，但默认不回迁已经稳定落在其他设备上的任务，除非能够减少硬违约且迁移成本可接受。

#### 5.16.6 双方案输出与人工确认

- **方案A 最少扰动**：冻结范围更大，优先保持现有设备、批次和时间，只迁移直接受影响任务；适合临近执行和车间稳定性优先场景。
- **方案B 最少违约损失**：允许移动更多未开工任务，优先降低不可延期和高罚款订单损失；适合产能变化较大或交付风险优先场景。

接口返回必须包含：`candidate_schedule_version`、方案名称、事件信息、移动/新增/取消任务清单、受影响订单、前后KPI、总违约损失变化、三工序利用率变化、换型变化、硬约束校验、无法排入订单及逐单原因。人工确认前仅为候选版本；确认后才发布，拒绝或校验失败则保留原排程。

#### 5.16.7 设备增减验收标准

- 新增设备在生效前、移除设备在生效后均不得出现任务；
- 已完成数量与剩余数量守恒，不重排已完成任务，不重复生产；
- 已开工、已锁定及冻结窗任务的处理符合企业选择并有审计记录；
- 设备、工艺顺序、换型、2小时交接和72小时等待均为0项违反；
- 不可延期订单不使用3天容忍窗，可延期订单不超过其人工维护的容忍上限；
- 两个方案都给出相对原排程的任务扰动数、违约损失和利用率变化；
- 算法失败时原排程不被修改，所有试排任务完整回滚；
- 同一事件和同一版本重复提交必须幂等，不得重复增加或移除设备；
- 设备增减前后结果绑定事件、输入数据、算法、配置和排程版本，可完整回放。
