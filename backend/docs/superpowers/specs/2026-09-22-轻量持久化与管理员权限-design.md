# 轻量持久化与管理员权限设计

## 1. 目标

在不改动排产算法、不重构现有页面的前提下，为人工业务操作增加重启后恢复能力，并为会改变系统状态的接口增加最小管理员权限。

成功标准：

- 服务重启后，人工优先级、延期策略、设备事件、订单删除、完工归档和已发布急单仍然存在。
- 页面查看无需登录；修改操作必须经过管理员验证。
- 原有排产结果、历史甘特图和 144 项测试保持兼容。
- 数据库写入失败时接口明确失败，不出现“页面提示成功但没有保存”。
- 修改可以通过 Git 标签和数据库备份快速回滚。

## 2. 范围

### 本期包含

- SQLite 单文件数据库。
- 单管理员密码。
- 短期管理员会话。
- 人工业务操作持久化。
- 启动恢复、事务、审计记录、备份与测试。

### 本期不包含

- 用户注册、多用户、部门和复杂角色体系。
- 修改排产目标函数、设备适配规则或 KPI 算法。
- 用数据库替代订单和产品额定 Excel 原始数据。
- 大规模前端重构。
- 公网单点登录、OAuth 或企业 AD 集成。

## 3. 总体架构

保留现有 `server.py -> scheduler/*` 调用关系，在 API 与运行内存之间增加一层独立的持久化适配器：

1. Excel 仍是原始订单和产能数据源。
2. SQLite 只保存人工操作和正式发布结果，作为可审计的覆盖层。
3. 排产引擎继续使用当前内存对象计算，不读取数据库内部表结构。
4. 服务启动时先加载 Excel，再按时间顺序重放 SQLite 中的有效操作。
5. API 修改成功且硬约束校验通过后，使用单个数据库事务保存操作和审计记录。

新增文件建议为 `backend/scheduler/persistence.py`。`server.py` 只调用其公开方法，不直接编写 SQL。

## 4. 数据库位置与配置

默认数据库：`backend/runtime/scheduler.db`。

可用环境变量 `SCHEDULER_DB_PATH` 覆盖。`backend/runtime/` 保持在 `.gitignore` 中，不提交运行数据。

管理员密码只通过环境变量 `SCHEDULER_ADMIN_PASSWORD` 注入，不写入数据库或日志；登录时使用恒定时间比较验证。数据库只保存会话令牌的单向摘要，不保存原密码或原始 token。若未配置管理员密码，服务保持只读模式，所有修改接口返回明确的 `503 admin_not_configured`，不能静默放行。

## 5. 最小数据模型

### `operations`

- `id`：操作 UUID。
- `operation_type`：`priority`、`delay_policy`、`device_event`、`order_delete`、`completion_archive`、`rush_publish`。
- `entity_id`：订单号、设备号或正式计划版本号。
- `payload_json`：完成恢复所需的结构化参数。
- `operator`：管理员显示名，第一阶段默认 `admin`。
- `created_at`：北京时间 ISO 时间。
- `status`：`active` 或 `reverted`。
- `reverts_operation_id`：撤回操作指向的原操作，可空。

### `admin_sessions`

- `token_hash`：会话令牌摘要。
- `created_at`、`expires_at`、`revoked_at`。

### `schema_meta`

- 保存数据库结构版本，支持以后做小型迁移。

所有建表使用 `CREATE TABLE IF NOT EXISTS`。数据库开启 WAL 模式、外键和合理的 busy timeout。

## 6. 权限模型

### 公开接口

- 静态页面。
- 健康检查。
- Dashboard、分析、问题、数据摘要。
- 排程状态和历史计划只读查询。

### 管理员接口

- 数据上传与确认。
- 正式排程运行和试排提交。
- 急单候选发布。
- 优先级、延期策略、设备事件。
- 订单删除、完工归档和撤回。

新增接口：

- `POST /api/auth/login`：提交管理员密码，成功后返回短期 bearer token。
- `POST /api/auth/logout`：吊销当前 token。
- `GET /api/auth/status`：返回是否已配置、当前 token 是否有效和过期时间。

前端把 token 保存在 `sessionStorage`，关闭浏览器标签后自动丢失。默认有效期 8 小时。所有受保护请求通过现有 `backend-bridge.js` 统一附加 `Authorization: Bearer <token>`。

鉴权失败统一返回：

- `401 auth_required`：未登录或 token 无效。
- `403 auth_expired`：会话已过期或被吊销。
- `503 admin_not_configured`：服务端未配置管理员密码。

## 7. 操作持久化与恢复

### 优先级与延期策略

先在当前引擎副本上应用并完成重排校验；校验通过后写入 `operations`，再替换正式内存状态。启动时按操作时间重放。

### 设备事件

保存完整设备事件参数。启动时按时间重放有效事件，无法再应用的历史事件记入恢复告警，不中断整个服务启动。

### 订单删除

增加后端删除接口。删除表示从当前正式计划覆盖层中排除，不修改原始 Excel。撤回通过新增一条反向操作实现，不物理删除审计记录。

### 完工归档

增加后端归档与撤回接口。保存真实完工时间、准时判定模式、操作者和关联计划版本。前端不再只维护 `archiveRecords` 内存数组。

### 正式急单

正式发布时保存急单原始输入、选中候选、确认人、原因和计划版本。启动恢复时先把急单恢复进订单覆盖层，再应用后续人工操作。

### 恢复顺序

1. 加载已确认的数据集或仓库默认 Excel。
2. 恢复正式急单。
3. 恢复订单删除和完工归档状态。
4. 恢复优先级与延期策略。
5. 恢复设备事件。
6. 运行一次正式排程并核对硬约束。

恢复失败时保留原始 Excel 基线，并把具体失败操作写入健康检查的 `restore_warnings`；不得跳过失败后继续声称全部恢复成功。

## 8. 原子性与错误处理

- 每个修改请求持有现有 `_LOCK`，避免同时修改正式计划。
- 在副本上计算和校验，成功后开启 SQLite 事务。
- 数据库提交成功后才替换正式 `STATE`。
- 数据库提交失败时回滚事务，不修改正式内存状态。
- 正式急单发布继续保存历史甘特图；历史留档失败时返回清晰警告，但正式状态与数据库记录必须一致。
- 前端收到 `401/403` 时弹出管理员验证框，验证后仅重试一次原操作，防止重复发布。

## 9. 前端最小改动

- 新增一个复用的管理员验证弹窗，不新增独立登录页面。
- `backend-bridge.js` 统一管理 token 和受保护请求。
- 优先级、删除、归档、设备操作和急单发布改为后端成功后再更新页面。
- 页面顶部仅显示小型状态：`只读`、`管理员已验证`或`会话已过期`。
- 保持现有布局、导航、甘特图和视觉风格不变。

## 10. 兼容与迁移

- 第一次启用数据库时不导入浏览器里已有的临时归档和删除记录，因为这些记录缺少可信操作者和服务器时间；页面应明确提示旧的本地临时状态不会成为正式记录。
- 现有历史甘特图 JSON 不迁入 SQLite，继续由 `ScheduleHistoryStore` 管理。
- 现有上传数据目录保持不变。
- API 响应尽量保持现有字段，只增加 `persisted`、`operation_id` 和权限错误结构。

## 11. 备份与回滚

实施前创建 Git 标签，例如 `before-persistence-auth-20260922`。

数据库每次结构升级前复制为带时间戳的 `.bak`。回滚步骤：

1. 停止服务。
2. 切回备份 Git 标签或上一提交。
3. 保留 `scheduler.db`，旧代码不会读取它。
4. 必要时把 `.bak` 恢复为正式数据库。

该设计不修改 Excel，因此原始业务数据始终可恢复。

## 12. 测试与验收

### 单元测试

- 数据库初始化和重复初始化。
- 操作写入、读取、撤回和事务回滚。
- 密码校验、token 过期和吊销。
- 未配置密码时只读保护。

### API 测试

- 所有 GET 只读接口无需 token。
- 所有修改接口无 token 返回 401。
- 登录后修改成功并返回 `operation_id`。
- 重复发布或重复重试不会生成两条正式急单。
- 上传文件大小和类型受到限制。

### 恢复测试

- 执行优先级、延期策略、设备事件、删除、归档和急单后重建应用状态，结果保持一致。
- 单条损坏操作产生恢复告警，不污染其他有效记录。
- 旧的 144 项测试继续通过。

### 浏览器验收

- 查看页面不要求登录。
- 首次修改弹出管理员验证。
- 验证后 8 小时内不重复询问。
- 会话过期后不会丢失表单内容，重新验证可安全重试。
- 刷新页面和重启后端后，正式业务状态保持一致。

## 13. 实施顺序

1. 先加数据库模块与单元测试，不接入现有接口。
2. 接入认证中间层并保护修改接口。
3. 逐项接入优先级、延期策略和设备事件。
4. 接入订单删除与完工归档。
5. 最后接入正式急单恢复。
6. 增加前端验证弹窗和会话状态。
7. 运行完整测试和重启恢复验收。

每一步都保持可独立提交和回滚，避免一次性大改。
