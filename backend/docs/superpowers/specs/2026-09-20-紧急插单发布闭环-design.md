# 紧急插单发布闭环设计

## 目标

计划员提交急单后由后端生成真实候选排程；确认某一方案后，将急单和候选排程原子发布为正式状态。订单中心、甘特图、风险预警和 KPI 随即读取同一正式版本，刷新页面后不丢失。

## 状态流

1. `POST /api/replan` 接收急单事实并运行 `Replanner`，只生成候选，不修改 `STATE['base']` 与正式订单池。
2. 后端为本次候选生成不可猜测的 `candidate_version`，暂存两个方案的 `ScheduleResult`、事件和影响信息。
3. 前端显示后端返回的方案，不再生成前端候选设备或伪造 KPI。
4. 计划员提交 `candidate_version / option_id / confirmed_by / reason` 到 `POST /api/replan/apply`。
5. 后端在锁内校验候选仍属于当前基线版本、急单已完整排入且硬约束通过，然后一次性更新正式订单池和 `STATE['base']`，写审计日志并返回新 dashboard。
6. 前端应用新 dashboard，并重新渲染订单中心、甘特图、风险预警和 KPI。

## 失败策略

- 急单无法完整排入时，候选方案标记为不可应用，并返回最早交付信息与原因；前端不得显示“确认成功”。
- 候选版本不存在、已发布、基线已改变、操作者为空或原因为空时拒绝发布。
- 同一候选重复提交必须幂等：返回已发布版本，不重复添加订单或任务。
- 发布前后均保留原订单号唯一性；重复订单号拒绝进入候选。

## 审计字段

`candidate_version / option_id / confirmed_by / confirmed_at / reason / inserted_order_ids / before_kpi / after_kpi`。
