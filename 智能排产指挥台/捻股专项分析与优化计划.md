## 三、三层根因

### 根因一：「生产」是瞬时快照，不是"今天有没有活"

`presenter.build_dashboard()` 的状态判定只有三行：

```python
cur = next((t for t in win if t.start <= now < t.end), None)
status = 'idle'
if cur is not None: status = 'normal'        # 此刻正在加工
elif cur_co is not None: status = 'change'   # 此刻正在换型
elif win: status = 'queued'                  # 窗口内有任务，但没轮到此刻
```

捻股 47 台是 `queued`（已派单、任务排在未来时段），**不是 `idle`（没活）**。

**准确描述应该是**：捻股此刻有 3 台在加工，47 台在排队等轮到。

### 根因二：订单量喂不饱 50 台捻股机

143 单 → 226 个生产批 → 捻股分不到均量。再叠加物理事实：

- **捻股单批只要 2–6 小时**（如 `捻股批次 2/2：5.2h（股长 8,240m）`）
- **拉丝单批动辄 20–90 小时**（如 `拉丝批次 10/12：586.1h`）

所以拉丝 47 台台台有长活、看起来满产；捻股同一时刻只开 2–3 台，**是数学上正确的结果**。

### 根因三：算法刻意"集中使用少数机台"

`engine.py::_place_batch` 的选机排序：

```python
if mode == 'asap':
    cand = (e, co, load)      # 最早完工优先
else:
    cand = (co, load, e)      # ← 换型最小 → 负荷均衡 → 完工
```

**换型优先级高于负荷均衡**。换型按股径分五档、最多扣 5h，同股径批次被连续吸到同几台机上。

这正是 `算法markdown\11_交付优先下的设备利用率优化方案.md` 的明确要求：

> 订单工作量不足时**应集中使用部分适配设备**，让启用设备保持合理负荷，其余设备作为备用或安排维护；不能要求所有设备同时达到高利用率。

### 加重误读的坑：`capacity` 字段口径

`capacity` = `busy_hours / (14 × 24)`，是**整个 14 天窗口的平均利用率**，不是当前占用率。

例：8203 正在加工，卡片显示 **6%**；8250 正在加工，显示 **12%**。**正在满负荷干活 ≠ 数字好看。**

## 四、用户追问的天花板：反直觉的关键数字

用户希望"捻股多开几台"，但实测给出一个反直觉结论：

> **738.5 机时 ÷ 50 台 = 每台仅 14.8 小时**

14 天里每台机器只忙**半天多**。

**所以"把所有捻股机都开起来"在数据上不成立**：

1. 摊薄后每台更闲，问题从"只有 1 台在跑"变成"50 台全部半死不活"，观感**更差**
2. 换型次数会爆炸（当前 2123 次 / 2451 小时，已是全厂主要损耗）
3. 违背 `11_交付优先` 文档的明确口径

**真正的优化方向不是"铺开"，而是「少而满」或者「把窗口调对」。**

## 五、四条优化路径

### 🟢 C：只改展示口径 —— 零算法风险，**最推荐**

| 改动 | 效果 | 代价 |
|---|---|---|
| `WINDOW_DAYS` 14 → 7 | 同时开工机台 3 → 约 **25 台**，**换型次数一次不变** | 0（需声明窗口为自定口径） |
| UI 的 `capacity` 加「14 天平均负荷」标注 | 消除"正在加工却显示 6%"的误读 | 0 |
| 设备态势页 `queued` 与 `idle` 分列 | 47 台"有活没轮到"一眼可见 | 0 |

**主因判断**：`WINDOW_DAYS = 14` 是把捻股摊薄到不起眼的首要原因。

### 🟡 A：JIT 排序把负荷均衡提前

```python
# 现状
cand = (co, load, e)
# 改为
cand = (load, co, e)
```

| 项 | 现状 | 改后（推算） |
|---|---|---|
| 同时开工机台数 | 3 | 约 **12** |
| 换型次数 | 2123 | 约 **3600**（+70%） |

**风险最高** —— 动的是字典序口径本身。评审若追问"为什么换型涨了 70%"，需要有说法。

### 🟡 B：放宽拆批上限

`config.BATCH_MAX` 12 → 24。

| 项 | 现状 | 改后（推算） |
|---|---|---|
| 同时开工机台数 | 3 | 约 **18** |
| 换型次数 | 2123 | 约 **4200** |

**可行性依据**：订单量中位数 2000 米、p75 4000 米、34 单超 5000 米，拆细的空间**确实存在**。代价是增加管理复杂度。

### 🔵 D：换叙事，不改代码

按 `11_交付优先下的设备利用率优化方案.md`，38 台闲置**不是缺陷，是设计目标** —— 它们是**应急产能**。

只要在答辩时把"为什么集中使用少数机台"讲透，反而能拿"约束可解释性"那 15 分。

**成本最低，收益可能最高。**

## 八、答辩话术要点

### 若被问「为什么捻股只有几台在跑」

> 页面上的"生产"是**瞬时快照**。捻股 50 台中此刻 3 台在加工、47 台是"已排产"（已派单、任务排在未来时段），全厂真正闲置的只有 1 台。
>
> 订单侧 143 单进入本 14 天窗口，只生成 226 个生产批，捻股总负荷 738.5 机时，摊到 50 台每台只有 14.8 小时 —— **活本身就不够**。
>
> 同时，我们的算法**刻意集中使用少数适配设备**：换型最小优先于负荷均衡，同股径批次连续生产，把换型损耗从分散排产的数千次压到 2123 次。这是《交付优先下的设备利用率优化方案》的明确设计，其余 38 台作为**应急产能与维护备用**，不是浪费。

### 若被问「利用率为什么这么低」

> 全厂 109 台平均利用率 4.88%，拉丝 89.9% 已是瓶颈，合绳 38.2% 闲置。**利用率低的主因是订单工作量不足**（302 单中仅 83 单可保证准时，覆盖率 27.48%），而不是排程不佳。文档已说明这种情况下应集中使用部分设备，不要求所有设备同时高利用率。

### 主动声明的口径

- **基准日 `BASELINE = 2026-09-19`、窗口 `WINDOW_DAYS = 14` 均为我们自定，赛题未规定**
- 产能按台账月产量折算（月产 ÷ 30 天 ÷ 24h）
- 股径由绳径反推的部分标记为 `inferred=True`（前端标黄）

## 附录 C：术语法中对照

| 术语 | 含义 |
|---|---|
| `normal` | 生产 —— 此刻任务块覆盖快照时刻 |
| `queued` | 已排产 —— 窗口内有任务，但未到开工时刻 |
| `idle` | 待排 —— 窗口内无任何任务 |
| `risk` | 风险 —— 单机利用率 > 95%（`CONGESTED_RATE`） |
| `change` | 换型 —— 此刻换型块覆盖快照时刻 |
| `capacity` | **14 天窗口平均利用率**，非瞬时占用率 |
| JIT | Just-In-Time，倒排（贴近交期反向排布） |
| ASAP | 尽早排布 |
| 换型键 | `rope\|绳径\|结构` / `strand\|股径` / `wire\|丝径` |
